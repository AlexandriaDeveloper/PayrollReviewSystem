# المعايير الهندسية العشرة — نظام مراجعة الصرفيات

**الحالة:** مبادئ جودة معتمدة بقرار المالك [ADR-005](../decisions/ADR-005-engineering-quality-and-agent-skills.md)؛ التفاصيل التنفيذية والتقنية النهائية **لم تُحسم**. استخدام `GEMINI.md` والمهارات المحلية لا يتجاوز تفويض الكود. [تعريف الاكتمال](DEFINITION-OF-DONE.md) معيار الأدلة. تنطبق المعايير بحسب أثر التغيير، مع أسباب صريحة للاستثناء.

## 1. TDD + Regression Testing
- قبل تنفيذ قاعدة مالية جديدة: صِغ سلوك القبول والعينة الاصطناعية، حالة نجاح، حالة فشل، ونقص بيانات وحالات تاريخية وحسابات طرفية. اتبع دورة `Red → Green → Refactor` عندما تسمح المهمة والأدوات، واحتفظ بإثبات حدوثها إن ادعيت ذلك.
- عند Bug قابل لإعادة الإنتاج: اختبر نفس الفشل أولًا، ثم أصلحه، ثم تحقق من اختفاء الفشل وعدم كسر العقد السابق. لا تختلق حالة فشل إذا لم تتوفر بيئة التنفيذ؛ `NOT_RUN` وتبرير.
- **طبقات الاختبار حسب المخاطر:** Unit للدومين دون ORM/PDF؛ Integration لقاعدة البيانات الفعلية والتزامن/الهجرات والمحولات؛ Contract لعقود API وAdapters؛ Security للحدود؛ End-to-End للرحلات الحرجة؛ Property-based / invariant tests للحساب والمجاميع ونسخ التاريخ حين تفيد.
- `Coverage %` مؤشر مساعد لا ضمان للصحة المالية. لا تقيس عدد Assertions بدل إثبات السلوك.
- اربط الاختبارات المحددة في المواصفات `TR/PG/FL/AC/SOLID/DDD` بأدلة التشغيل، ولا تصف اختبارًا تصوريًا بأنه منفذ.

## 2. KISS + DRY + YAGNI
- ابدأ بأبسط تصميم يحقق الثوابت ومعايير القبول وقابل للتغيير المتوقع؛ تجنب `God Service`، لكن لا تصنع `interface` أو `Factory` لكل كلاس.
- `DRY` يحارب **تكرار معرفة تجارية واحدة** وليس التشابه السطحي في سطرين. لا تجمع قاعدتين قانونيتين مختلفتين في معادلة عامة لمجرد تطابق أرقام مؤقتة.
- `YAGNI`: لا Microservices أو Rule DSL عامة أو Event Bus أو CQRS كامل دون حاجة موثقة، ولا Extensions استباقية لا تستند إلى متطلب.
- كل Abstraction يذكر سببًا: حماية Contract أو تبديل Adapter فعلي أو عزل سياسة أو اختبار. راجع [OOP وSOLID](../architecture/OOP-AND-SOLID-DESIGN-STANDARDS.md).

## 3. Database Integrity + ACID + Concurrency
- لا تعتمد قاعدة `MonthlyMainSalarySlot` على `if not exists` وحده؛ تصميم قيد فريد `(UnitId,EmploymentRelationshipId,SalaryEntitlementMonth)` وTransaction مناسبة لحماية إنشاء مرتب MAIN من طلبين متزامنين. اختيار SQL/DDL النهائي ينتظر الموافقة.
- نسخ `MainSalaryRevision` و`AuditCase` تحفظ تغييرات المراجع بإصدارات و`OptimisticConcurrency` أو سياسة معتمدة؛ لا `last-write-wins` دون كشف تعارض.
- علاقة `SEPARATE` متعددة، و`SourceFinancialOccurrence` تكرر نفس الكود بصورة مشروعة؛ لا تضع قيد فرادة في مكان خاطئ.
- التسويات لا تتجاوز سند الدفع/الدين المثبت، والتوزيع على أكثر من التزام يتطلب اتساقًا ومنع `double allocation`؛ اختبار متوازٍ إلزامي لتغييرها.
- المهاجرات تُختبر على **Database Provider الحقيقي المختار**، وتشمل الأثر على البيانات القديمة وفهرسة/تراجع أو `forward-fix` آمن عند عدم إمكان rollback. لا حذف أدلة مالية ولا `CascadeDelete` صامت.
- معاملات ACID مهمة حيث يجب الثبات الفوري؛ لا تضع كل النظام داخل Transaction عامة واحدة.

## 4. Deterministic Financial Calculations
- المال `decimal` بدقة مناسبة؛ لا `float/double` في المبالغ؛ التعامل مع الضرائب والاستقطاعات وفق تحديد `Scale/Precision` وقواعد التقريب والسند المعتمد لكل بند.
- نتيجة الحساب تتحدد بواسطة `Person/PayeeRelationship`, `FinancialComponent`, `TimeSlice`, `ValidAt/KnownAt`, `ApprovedFactsSnapshot`, `RuleVersion`, `RoundingPolicyVersion`، وليس وقت تشغيل النظام أو الدرجة الحالية.
- القاعدة القانونية غير المثبتة أو الوعاء الناقص `UNKNOWN/INPUT_MISSING`، لا `0` ولا استحقاق مصادقًا عليه.
- `RuleTrace` يسجل المراجع الزمنية والإصدار والمدخلات والأثر والتقريب، بحيث يمكن إعادة إنتاج مراجعة قديمة.
- `SourceAmount`, `ExpectedAmount`, `ReviewedAmount`, `OfficialCorrectionAmount`, `VerifiedPaidAmount` قيم منفصلة؛ لا تغير مراجعة واحدة أي قيمة أصلية.

## 5. Idempotency + Safe Retry
- أعد تقديم نفس طلب الاستيراد أو الموافقة أو تسجيل مرشح MAIN دون تكرار **الأثر المالي المنطقي**. استخدم `IdempotencyKey` أو بصمة/هوية عملية في المستوى الصحيح مع قواعد تنافس ومعالجة انتهاء صلاحية المفاتيح عند اللزوم.
- إعادة استقبال المصدر لا تُسقط `ImportAttempt` أو `SourceOccurrence` تاريخيًا، ولا تولد مرتبًا جديدًا للمستند نفسه.
- لا تجعل التشابه في المبلغ/الكود معيارًا لمنع **صرفيتين SEPARATE صحيحتين**. يختلف `technical duplicate` عن `business legitimate repetition`.
- عند فشل جزئي في استيراد ملف أو حفظ قرار: أظهر الحالة القابلة للاستئناف أو التعويض، ولا تدعِ `Committed` من غير ضمان؛ حدّد متى يُسمح بالـRetry.

## 6. API-First Contracts + Error Handling
- صِغ لكل Use Case عقد مدخلات ومخرجات وأخطاء قبل التنفيذ، مع `ID/Version/EffectivePeriod` عند الحاجة. API Versioning والتوافق يبنيان على الاحتياج الفعلي.
- حالات الخطأ مثل `INPUT_MISSING`, `RULE_CONFLICT`, `DUPLICATE_MAIN_CANDIDATE`, `CONCURRENCY_CONFLICT`, `NOT_AUTHORIZED`, `SOURCE_REVIEW_REQUIRED` تُقدّم بشكل مستقر، ولا تخلط `Reviewed` أو `VerifiedPaid`.
- لا تبتلع الاستثناء أو تُرجع `200 OK` مع اعتماد لم ينجح؛ لا تعرّض StackTrace أو بيانات مالية حساسة للمستخدم.
- التحقق في الخادم وليس الواجهة فقط، مع رسائل عربية واضحة وخانات إنجليزية ثابتة للمفاتيح والأكواد؛ دعم RTL دون إفساد القيم.

## 7. Security by Design + Auditability
- `Least Privilege` و`RBAC` على الخادم حسب الوحدة والمجموعة والدورة ونوع الصرف والعمل؛ مسؤول النظام لا يرث صلاحية الاعتماد المالي تلقائيًا.
- امنع وصول مستخدم إلى `ObjectId` لموظف خارج مجموعته حتى لو غيّر رابط API أو `Query`؛ اختبر `IDOR` والحالات متعددة المستخدمين.
- لا بيانات موظفين فعلية في GitHub أو CI أو Screenshots أو Logs. تحقق من Uploaded PDF/Excel من النوع والحجم والمحتوى، وحدود المعالجة وFormula Injection عند التصدير.
- `Audit Trail` يسجل انتقال الحالة ومن فعل القرار والسبب والنسخة والمستند وتاريخ العلم، ويقاوم المحو الصامت؛ ليس مجرد LogDebug.
- `Threat Model` وتشفير وحفظ أدلة المصادر والنسخ الاحتياطي والاستعادة تُختبر قبل استخدام بيانات حقيقية.

## 8. Observability + Structured Logging
- عرّف `CorrelationId` لكل Request/Import/Calculation/Review، وتوقيت العملية ومعرفاتها الفنية المحايدة وإصدار المحول/القاعدة عند اللزوم.
- مستويات `Info/Warn/Error` منظمة، أسباب الفشل وتصنيفها، وفصل Telemetry التشغيلية عن السجل المالي القانوني.
- لا تُسجل الرقم القومي أو الراتب الكامل أو بيانات ملف PDF أو رموز المصادقة. اختبر مسارات الخطأ أيضًا بحثًا عن التسريب.
- سجّل مؤشرات: نسبة الاستيراد `ReviewRequired`، الزمن، التعارضات، retries، وQueue Backlog عند وجود عامل معالجة، دون بناء منصة Monitoring خارج الحاجة.

## 9. Performance + Scalability by Measurement
- لا تحمل جميع موظفي الشهر وملفات PDF في Aggregate واحد؛ استخدم معالجة دفعات/Streaming عند الضرورة ومؤشرات تقدم و`Pagination` حسب متطلبات UI.
- `Async I/O` للقراءة/الكتابة غير المتزامنة المناسبة؛ لا تنشئ Task لكل سطر مالي أو توسعًا غير مضبوط. التزامن يجب أن يحافظ على اتساق النتائج.
- اختبارات أحمال ببيانات **اصطناعية**؛ قبل اعتماد ميزانية الأداء اطلب أحجام الملفات والمراجعين والصفحات الفعلية، ولا تخترع حدودًا رقمية كمتطلبات معتمدة.
- القياس قبل التحسين: وقت الطلب وحجم الذاكرة والخطأ وأثر الفهارس وتكاليف الاستيراد. لا تغير قاعدة مالية لأجل السرعة دون موافقة واختبارات.

## 10. CI Quality Gates + Safe Delivery
- على PR برمجي **مصرح به**: تحقق من Build وUnit/Integration/Contract حسب المخاطر، وتحليل ثابت وتنسيق، وفحص أسرار واعتمادات Security/Dependency المناسبة، وArchitecture/Boundary tests عند التغيير المعماري.
- لا تعدل CI/Branch Protection أو تثبت Dependencies تلقائيًا في هذا القرار؛ إعداد CI الفعلي مهمة منفصلة معتمدة.
- قدّم Output حقيقيًا للأوامر و`Commit SHA` وبصمات الاختبارات؛ `NOT_RUN` ليس `PASS`، و`N/A` يحتاج سببًا وبدائل متناسبة.
- التغييرات في البيانات والإصدارات تحتاج خطة `Migration + Backup/Restore + Rollback or Forward-Fix` قابلة للتحقق، وإطلاقًا خاضعًا لقرار المالك؛ Gemini لا يدمج كوده ولا ينشره.

## قابلية التطبيق/استثناءات مبررة
- **توثيق فقط:** يلزم الاتساق وصحة الروابط والحكومة، ولا ندعي اختبارات كود.
- **Bug Fix:** `Regression` ونتائج فشل/نجاح حسب القدرة، مع فحص أثره على العقود والبيانات.
- **تغيير مالي أو تعاملي:** `Determinism`, `DB/Concurrency`, `Idempotency`, و`Security` اختبارات جوهرية؛ تعذر تشغيلها مانع لمطالبة الدمج حتى يتوفر دليل بديل معتمد.
- **UI فقط:** RTL/Accessibility والتحقق من عدم تغيير حساب أو صلاحية على الخادم؛ لا نفرض Migration أو اختبارات أداء DB بلا صلة.
- **Migration/Deployment:** تفويض صريح مستقل، وإثبات النسخ الاحتياطي والترحيل الآمن والرجوع قبل العمل على بيانات مهمة.
