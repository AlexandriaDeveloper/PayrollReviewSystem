# ADR-004 — اعتماد OOP وSOLID مع DDD وClean Architecture

**الحالة: ACCEPTED — قرار منهجي معتمد من المالك.**
**التاريخ:** 7 نوفمبر 2026.
**المستودع:** `AlexandriaDeveloper/PayrollReviewSystem`.
**Issue:** [#31](https://github.com/AlexandriaDeveloper/PayrollReviewSystem/issues/31).
**المرجع السابق:** [ADR-003 — DDD + Modular Monolith + Clean Architecture](ADR-003-ddd-modular-monolith-clean-architecture.md).

## السياق
وافق المالك على تنظيم المشروع بأسلوب `DDD` و`Modular Monolith` و`Clean Architecture`، وأضاف شرطًا تصميميًا/تنفيذيًا هو `Object-Oriented Programming (OOP)` و`SOLID Principles`. يشمل النظام قواعد مرتبات متغيرة تاريخيًا، وصرفيات رئيسية ومنفصلة، ومصادر Oracle/Excel/مدخلات شاشة، وإقرارات مراجعة، ومتجمدات واستقطاعات مشروطة. الحفاظ على صحة قواعد الأعمال والحدود بين هذه المسؤوليات أهم من تكثير الكلاسات والواجهات.

## القرار
1. **OOP** أسلوب أساسي لتنفيذ نموذج الأعمال، مع مراعاة `Encapsulation`, `Abstraction`, `Polymorphism` واستخدام `Inheritance` فقط عند ثبوت علاقة `is-a` صالحة تحافظ على العقد. تمثَّل كيانات الدومين و`Aggregates` والـ`Value Objects` بقواعد صريحة وعمليات تحمي الثوابت؛ لا تعتمد على `public setters` المفتوحة لأحداث المراجعة والحساب.
2. **SOLID** مجموعة معايير هندسية إلزامية عند تصميم أو مراجعة الكود؛ تستخدم بحكم وسياق، لا كمبرر لإنشاء `interface` لكل كلاس أو طبقة تجريد بلا حاجة. راجع [الدليل التفصيلي](../architecture/OOP-AND-SOLID-DESIGN-STANDARDS.md).
3. **SRP:** مسؤولية تغيير واحدة لكل نوع/وحدة متماسكة؛ لا `God Class` يجمع PDF parsing والحساب والاعتماد والتسوية.
4. **OCP:** أضف `Adapter` لقناة مصدر جديدة، أو `RuleEffect`/سياسة مالية بإصدارها ومجالها، دون تعديل منطق غير مرتبط؛ **مع** منع التنشيط التلقائي لأي قانون جديد بلا سند واعتماد.
5. **LSP:** كل تنفيذ `Port` يلتزم بالوعود المعلنة، ويحافظ على هوية سطور المصدر ودقة المبلغ والحالة وعدم الادعاء بأنه مستند Oracle رسمي. لا توريث يخفي تغيّر معنى `Source` و`Expected` أو `Verified`.
6. **ISP:** واجهات ضيقة بحسب حالة الاستخدام؛ لا تجبر محرك الحساب على عمليات أرشفة PDF أو خدمة إدخال Excel على واجهات اعتماد مالي.
7. **DIP:** `Domain` لا يعتمد على `ORM` أو `SQL Server` أو `PDFium` أو `Angular` أو `HttpClient`; عقود `Ports` تتحدد بحسب حاجات `Domain/Application` وتنفذها `Infrastructure`. `Dependency Injection` آلية ممكنة وليست مرادفًا لـDIP.
8. **Composition over Inheritance** افتراضيًا عند اختلاف القنوات والتواريخ والقواعد؛ الوراثة ليست ممنوعة، لكن تحتاج ضمان صحة العقد وعدم زيادة التشابك. يمكن استخدام `records`, `DTOs`, `pure functions` و`data-oriented` تمثيلات بسيطة لأجزاء ذات قيمة؛ **OOP لا يعني أن كل قيمة أو إجراء يجب أن يكون كلاسًا مليئًا بالطرق**.
9. اختبارات الحدود والـInvariants والتزامن والتواريخ والخصومات وسلامة المصادر تتقدم على الاستعراض الشكلي لـSOLID؛ تغيير تصميم جوهري يمر بمراجعة `EGM Goldfish` مستقلة قبل إذن الكود.

## نمط تطبيق المبادئ على النظام
- `MonthlyMainSalarySlot` يحمي فرادة المرتب الرئيسي المنطقي على مستوى علاقة العمل/الوحدة/شهر الاستحقاق؛ يُضيف `MainSalaryRevision` عبر عمليات مقيدة، ولا يُحوّل الصرفية المنفصلة إلى مرتب رئيسي. **التحقق في الكود وحده لا يكفي**؛ يحتاج قيد DB ذري بعد اعتماد التصميم الفيزيائي.
- `SourceIntake` يعرض عقدًا محايدًا لمصدر PDF/Excel/إدخال مباشر؛ يحافظ على كل `SourceFinancialOccurrence` حتى لو تكرر الكود، ولا ينشئ PDF رسميًا وهميًا.
- `Rules` يفصل اختيار القواعد الزمنية وتركيب `RuleEffects` والمرجع والـ`RuleTrace` عن عملية استخراج المصدر؛ لا تُفعّل نسبة افتراضية باسم OCP.
- `AuditCase` يحافظ على قرار المراجع وإصداراته؛ لا يغير مبلغ Oracle ولا يثبت الدفع؛ الالتزامات والتسويات تستلزم أدلة.

## النتائج والقيود
**الفوائد:** مراجعة أسهل، اختبار وحدات دون IO، قابلية إضافة قنوات وقواعد مضبوطة، وحماية حدود الدومين. **التكلفة:** عقود واضحة واختبارات سلوك وتوثيق المسؤوليات، واحتمال الإفراط في التجريد؛ تُراجع الكلفة باستمرار.

**غير مشمول بالاعتماد:** تصميم كلاسات C# أو API أو جداول أو `Dependency Injection` container محدد، تفاصيل `Bounded Contexts/Aggregates` المقترحة في ADR-003، إصدارات التكنولوجيا أو SQL schema، التوثيق القانوني للنسب، أو السماح بالبرمجة. لا تُدمج تغييرات على ملفات هدف/مراجع Goldfish الجاري تشغيلها بسبب هذا القرار.
