# مراحل تنفيذ التصميم بواسطة Gemini

**الحالة: خطة لا تصريح برمجي شامل.** يملك ChatGPT تفويض دمج ملفات Markdown المراجَعة فقط؛ أما الكود ومخططات قاعدة البيانات الفعلية والهجرات فتحتاج Issues محددة مصرحًا بها واعتماد المالك.

## المرحلة صفر — تثبيت التصميم والتوثيق
راجع ERD الثلاثة وUML للكلاسات وتسلسل الاستخدام والحالات والشبكة الداخلية. وحِّد مصطلحات `Employees/EmploymentRelationship` و`FinancialRelationship/PayeeRelationship` و`ApprovedFinancialFact`. المخطط يصف ملكية البيانات وليس عدد الجداول الفعلي. **لا Migrations في هذه المرحلة**.

## المرحلة الأولى — استيراد مصادر Oracle
بعد التصريح:
1. حفظ أصل PDF بصورة مؤمنة وبصمة وإصدار.
2. خدمة `Parser Adapter` تحفظ كل ظهور للسطر وتتجنب دمج الأكواد المتكررة وتفسر العربية بحذر.
3. اختبارات صرفية الفرد والكافر وكشف الصرف والهوية والأرقام السالبة والاستحقاقات والاستقطاعات والصافي.
4. واجهة معاينة توضح ما تم إثباته وما يحتاج مراجعة وأدلة الصفحة والصف.
5. الاستفادة من `OraclePdfParser` و`PDF-EXTRACTOR` وفق [Issue #6](https://github.com/AlexandriaDeveloper/PayrollReviewSystem/issues/6) دون إعادة كتابة عمياء.
6. اختبار خاص على **أكثر من شكل PDF أصلي** في بيئة مخولة دون رفع البيانات الحقيقية إلى GitHub.

## المرحلة الثانية — بيانات المستفيدين والمراجعين
الوحدة الحسابية والكليات، `Person` و`EmploymentRelationship` و`PayeeRelationship`، مجموعات المرتب وصلاحيات المراجعين، الوقائع المالية والدرجات التاريخية ومرجع 2015، منع تحديثها من Oracle، وسجل من عدّل ومتى وآلية منع تعارض التحديثات.

## المرحلة الثالثة — المراجعة والتصحيحات
شاشة المصدر مقابل المتوقع، والفرق والتعليق وقرار المراجع، قبول الصناديق المحسوبة في المركزية، استثناء تجميع البنود بباب صرف واحد بعد مستند وموافقة، فصل اعتماد الفحص عن تصحيح المركزية، وإعادة فتح المراجعة بعد الحدث الطارئ.

## المرحلة الرابعة — القواعد ذات السريان والقرارات
كتالوج نصوص قانونية أصيلة وتواريخ وفئات، ومحرك ترقية وعلاوة وإجازة وجزء شهر **يقترح** النتائج. استبعاد إعادة حساب التأمينات عمومًا؛ حالة جزء الوقت بعد التثبت من مصدر الوعاء وسريان النص. الضرائب وتوسعات أخرى تخضع لمهام منفصلة.

### شروط إضافية قبل بناء Rule Engine
يجب تنفيذ التصميم أولًا بمواصفة [تداخل القواعد والقرارات](../specs/TEMPORAL-RULE-RESOLUTION-AND-CONFLICTS.md): `Bitemporal`، تقطيع الفترات، التحقق من الدرجات، ترجيح موثق بين القواعد، سياسة تجميع أثر بندين، `RuleTrace`، و20 حالة اختبار `TR-001..TR-020`. المثال المرتبط يوضح مسارًا متداخلًا دون معادلة خصم غياب مخترعة. يتطلب التنفيذ ADR ومهمة كود مصرحًا بها.

## المرحلة الخامسة — المتجمدات والتسويات
الفروق بالأثر الرجعي على مستوى البند والشهر والسبب، والربط بظهور مبلغ في كشف لاحق ثم بدليل تسوية مستقل، دون افتراض أن المبلغ صُرف أو تكرار مطالبة.

## المرحلة السادسة — التقارير والتحصين
Excel عربي، وتقارير مصدر ومراجعة، واختبارات أحمال مبنية على بيانات افتراضية، واستعادة نسخ احتياطية، وصلاحيات RBAC والفصل بين الموظفين والمراجعين، ومزامنة ERD مع مخطط SQL المعتمد.

## معايير اكتمال التصميم
- كل كيان له مالك وعلاقة ومفتاح وتاريخ/نسخ وصلاحيات.
- كل مبلغ محدد المصدر والصفة: وارد، متوقع، مُراجع، مصحح، ظاهر في الصرفية، أو مثبت الصرف.
- كل سطر في Oracle له دليل مستقل؛ لا دمج على الكود.
- لا نسخ تاريخية تُمحى عند ورود قرار جديد.
- لكل قرار مراجع فاعل وسبب ومصدر ونسخة وختم وقت.
- لكل API اختبارات نجاح وفشل ونقص بيانات وأكواد مكررة وتعارض تعديل.

## قرارات لا بد من اعتمادها قبل أجزاء محددة من الكود
1. التقنية النهائية وإصداراتها.
2. SQL Schema الفيزيائي والفهارس والمفاتيح وحدود المعاملات والحذف.
3. قواعد مطابقة هوية المستفيد من مصدر رسمي بين الكليات وأنواع الصرف.
4. تقارير Oracle وأنواع الجداول والتنسيقات المقبولة.
5. من يعتمد المراجعة ويقبل استثناء باب الصرف ومن يعيد فتح الصرفية أو يطلب إيقافها.
6. سند القانون والوعاء التأميني لحالة العمل جزءًا من الوقت بحسب الكادر.
7. قواعد حساب البنود المستقلة وأدلتها وتواريخ سريانها.
8. كود المجموعة البنكية وكيفية مطابقة الكافر وكشوف الصرف.
9. حماية السيرفر والمستخدمين والأرشيف والنسخ الاحتياطية وسرية بيانات الموظفين.
10. حجم مستخدمي النظام والصفحات ودورات الصرف وعينات الاختبار المخولة.

## قاعدة عدم إعادة العمل
قبل إنشاء Entity أو Migration يكتب Gemini مرجع القرار المعماري والكيان ومكانه والعلاقات والقيود والاختبارات. مخطط Mermaid المقترح **ليس تصريح إنشاء جدول**. ملف أمثلة [ERD](../examples/01-ERD-INPUT-OUTPUT.md) و[UML](../examples/02-UML-REVIEW-EXAMPLES.md) لشرح شكل البيانات فقط.

## مرحلة معمارية قبل أي تنفيذ: DDD وحدود الوحدات
**قرار النهج المعماري مقبول** وفق `ADR-003`؛ لكن تفاصيل `Bounded Contexts` و`Aggregate Roots` و`Context Map` في [التصميم المقترح](DDD-BOUNDED-CONTEXTS-AND-AGGREGATES.md) تتطلب مراجعة Goldfish منفصلة وقرارًا يحدد حدود الاتساق وملكية القراءة/الكتابة لكل Context. بعد مراجعة الحزم الأصلية، راجع هذا المستند الجديد بمراجع Fresh Context، ثم حل `BLOCKER/MAJOR` وأكمل ADR تخطيط SQL الفيزيائي قبل الكود.

**مطلوب في كل مهمة Gemini لاحقة:** إعلان `Bounded Context` و`Aggregate Root` و`Invariant` و`Application Use Case` و`Contract` و`Transaction Boundary` واختبارات التصميم المرتبطة قبل البرمجة؛ لا تجعل ORM يمحو ملكية البيانات، ولا تجعل ملف Oracle مصدر حقيقة الموظف. أي تنفيذ أو ترحيل يحتاج Issue مصرحًا بها منفصلة.

## متطلب OOP وSOLID قبل أي كتابة كود
المبادئ المعتمدة في [ADR-004](../decisions/ADR-004-object-oriented-and-solid-principles.md) و[دليل التصميم](OOP-AND-SOLID-DESIGN-STANDARDS.md) إلزامية على المهام البرمجية بعد اعتماد المالك:
- عرّف المسؤولية الواحدة لكل `Domain Entity/Aggregate/Application Service`، والـInvariant الذي تحميه، والعقود التي تحتاجها حالات الاستخدام فعلًا.
- وثّق لماذا استخدمت `Inheritance` أو `Composition` أو `Polymorphism`، وأن بدائل المصدر تلتزم `LSP` ولا تخلط درجات الإثبات.
- أثبت اتجاه التبعية الصحيح `Domain → no Infrastructure`، وحدود `Ports` والـ`Adapters` والفصل بين ORM وFinancial Rules.
- اكتب اختبارات نجاح/فشل وحالات التزامن لكل ثابت مالي، واربط `SOLID-001..018` بما يخص المهمة. **لا كود أو SQL الآن**؛ التفاصيل تُراجع Goldfish مع خريطة DDD قبل التصريح.

## مرحلة جودة التنفيذ — معايير Gemini وDefinition of Done
بعد انتهاء التصميم المعتمد وصدور موافقة مالك لكل Issue تنفيذ، يستخدم Gemini [Engineering Standards](../engineering/ENGINEERING-STANDARDS.md) و[Definition of Done](../engineering/DEFINITION-OF-DONE.md) و`ADR-005`، بالإضافة إلى `OOP/SOLID` و`DDD`.
- اختبارات Regression/Contract/Integration/Security اللازمة بحسب خطر التغيير، و`PASS/FAIL/NOT_RUN/N/A` بأدلة فعلية.
- حساب `decimal` حتمي ومصادر قوانين سليمة، تزامن وإنشاء MAIN واحد، SEPARATE متعددة، مصدر متكرر غير ممسوح.
- توافق عقود API، وضوح الأخطاء، RBAC في الخادم، Observability دون PII، واستيراد بكفاءة مقاسة على عينات اصطناعية.
- لا يُنشأ CI جديد ولا Migration إلا بتفويض منفصل، ولا يُعلن نجاح اختبار لم يتم تشغيله. لا يدمج Gemini كوده.
