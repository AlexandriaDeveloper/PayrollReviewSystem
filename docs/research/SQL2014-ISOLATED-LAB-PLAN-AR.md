## 1. الأدلة المتحقَّق منها مقابل المتطلبات غير المفحوصة (`Verified vs Unchecked`)

### أ) حقائق مُثبتة بالملاحظة المباشرة في فحص Gate A (`AI-0028` / `AI-0029`)
- المثيل المحلي الوحيد على جهاز المالك هو `MSSQLSERVER` (`MSSQL12.MSSQLSERVER`) قيد التشغيل، ولا توجد مثيلات مسماة أخرى أو `SqlLocalDB` (`NO_SQLLOCALDB`).
- هوية المحرك الموثّقة: `SQL Server 2014 Enterprise Edition (64-bit)`، بناء `12.0.2269.0`، مستوى `RTM` (`RTM GDR` بتاريخ بناء `Jun 10 2015`)، `EngineEdition = 3`، `IsIntegratedSecurityOnly = 0` (`Mixed Mode`)، و`compatibility_level = 120`.
- مؤشرات العزل: `LinkedServerCount = 0`، لكن المثيل يحوي `4` قواعد نظام و`2` قواعد `ReportServer` و**`13` قاعدة بيانات مستخدمين قائمة** (`8 ONLINE` و`5 OFFLINE`) تشير أسماؤها إلى موارد بشرية/مرتبات/إنتاج ومشاريع سابقة، ويستمع على كافة الواجهات الشبكية (`all interfaces:1433`).
- الحالة المسجّلة: **`BLOCKED_ISOLATION`** + **`BLOCKED_TLS_BUILD`** (لأن `12.0.2269.0 RTM GDR` يسبق بناء دعم `TLS 1.2` في `KB3135244`، والذي ينص لمسار `2014 RTM GDR` على أن دعم `TLS 1.2` يتاح عبر تثبيت `2014 SP2` أو `2014 SP3`؛ مع ملاحظة أن رصد `encrypt_option = FALSE` عبر `Shared Memory` لا يثبت وحده وضع TLS عبر `TCP`).

### ب) حقائق رسمية مُثبتة من وثائق Microsoft Learn (تاريخ الاطلاع: `2026-11-12/13`)
- توافق أنظمة Windows مع SQL Server (`KB2681562`, [Version requirements for SQL Server in Windows](https://learn.microsoft.com/en-us/troubleshoot/sql/database-engine/install/windows/use-sql-server-in-windows)، محدّثة `2026-08-05`):
  - **`Windows 11` و`Windows Server 2022` و`Windows Server 2025`:** **`Not supported`** لـ `SQL Server 2014`.
  - **`Windows Server 2019` و`Windows 10` و`Windows Server 2016`:** **`Yes (SP3)`** — أي يُشترط `SQL Server 2014 SP3`.
- دعم `TLS 1.2` (`KB3135244`, [TLS 1.2 support for Microsoft SQL Server](https://learn.microsoft.com/en-us/troubleshoot/sql/database-engine/connect/tls-1-2-support-microsoft-sql-server)):
  - مسار `SQL Server 2014 RTM GDR` يتطلب `2014 SP2` أو `2014 SP3`.
- تعارض وثائق `EF Core` مع `SQL Server 2014`: لا يزال موثقًا في [دراسة Phase A](SQL2014-DATA-ACCESS-COMPATIBILITY-AR.md) بحالة `CONFLICTING_OFFICIAL_DOCUMENTATION / NOT_ESTABLISHED`.

### ج) معطيات لم تُفحص بعد (`UNKNOWN / REQUIRED_EVIDENCE` — لا تُفترض)
- نسخة وإصدار `Windows` على جهاز المالك المضيف، وقدرة المعالج (`RAM / CPU / SSD`)، وتفعيل الافتراضية (`VT-x / AMD-V` و`Hyper-V`)، وتوافر وسائط تثبيت وتراخيص `Windows Server 2019 / Windows 10` و`SQL Server 2014 SP3` وتكلفتها (`UNKNOWN`).

## 2. قائمة حظر التجارب على المثيل الحالي (`DO NOT TOUCH` Baseline Protection)

تُفرض القائمة التالية بصرامة لحماية المثيل المشترك `MSSQLSERVER` والقواعد الـ13 القائمة عليه:

1. **يُحظر تمامًا** إنشاء قاعدة `PayrollReview_CompatLab_Synthetic` أو أي قاعدة اختبارية على `MSSQLSERVER`.
2. **يُحظر تمامًا** تنفيذ `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `INSERT`, `UPDATE`, `DELETE` أو قراءة (`SELECT`) جداول أيٍّ من القواعد الـ13 القائمة.
3. **يُحظر تمامًا** ترقية المثيل الحالي من `RTM (12.0.2269.0)` إلى `SP2/SP3`، أو تعديل إعدادات `TLS`، الشهادات، منافذ TCP، `Windows Firewall`، أو صلاحيات الدخول على المثيل الحالي ضمن مهام التطوير.
4. **يُحظر تمامًا** نسخ أو أخذ `Backup/Restore` من القواعد الـ13 أو من قاعدة بيانات الجامعة إلى داخل المعمل المستقل؛ يجب أن تكون بيانات المعمل **اصطناعية بنسبة 100%**.

## 3. مقارنة خيارات العزل (`VM vs Named Instance vs Dedicated Lab Server`)

| المعيار | الخيار 1: `VM` مستقلة ومعزولة *(المسار المفضل مبدئيًا)* | الخيار 2: `Named Instance` مستقل على نفس المضيف *(غير مفضل كعزل مكافئ)* | الخيار 3: خادم/VM معملي مؤسسي معزول *(خيار احتياطي)* |
| :--- | :--- | :--- | :--- |
| **مستوى عزل نظام التشغيل والعمليات** | **عزل منطقي ونظامي قوي (وليس عزلًا مطلقًا):** يفصل نواة الضيف ونظام التشغيل والـ`Services` والـ`Registry` والقرص الافتراضي، لكنه يظل يشترك مع المضيف في العتاد المادي والـ`Hypervisor` والتخزين وحالة أمن المضيف | **منعدم تقريبًا:** يشترك مع المضيف والمثيل المشترك في نفس نظام التشغيل والـ`Registry` والذاكرة والقرص والخدمات المشتركة (`SQL Browser`) | **عزل منطقي قوي على بنية مؤسسية منفصلة عن جهاز المطور** (مع بقاء التبعية لضبط الشبكة والصلاحيات في الخادم المؤسسي) |
| **التوافق الرسمي مع `SQL Server 2014` على نظام حديث** | يسمح بتشغيل ضيف مدعوم رسميًا (`Windows Server 2019 + SP3`) حتى لو كان المضيف `Windows 11` | إذا كان المضيف `Windows 11` فإن `SQL Server 2014` مصنف **`Not supported`** رسميًا عليه (`KB2681562`) | تحدده مواصفات الـVM/الخادم المؤسسي (`Windows Server 2019 + SP3`) |
| **مخاطر التداخل مع الـ13 قاعدة القائمة** | **مخاطر متبقية منخفضة ومشروطة بضبط التهيئة:** تنخفض عند حصر الشبكة بـ`Host-Only / Internal Switch` وتعطيل المجلدات المشتركة وتوجيه الأقراص؛ لكنها لا تنعدم مطلقًا (مثل اختناق RAM/CPU على المضيف أو خطأ ربط منفذ/شبكة) | **مرتفعة:** خطأ في المنفذ أو اسم المثيل أو تحديث مكون مشترك قد يؤثر على `MSSQLSERVER` أو يستنزف موارده أو يشارك أسطح الهجوم | **معزولة عن المضيف محليًا، بمخاطر متبقية محكومة بضوابط الشبكة** (يشترط عدم وجود أي مسار يصل لشبكة الإنتاج الجامعية) |
| **قدرة الرجوع السريع (`Rollback`)** | **ممتازة نسبيًا:** `VM Snapshot / Checkpoint` تعيد حالة الضيف قبل الاختبار مع بقاء مسؤولية التحقق من أي أثر شبكي أو محلي | **محدودة:** يتطلب إلغاء تثبيت يدوي وتبقى آثار `Registry` وملفات مشتركة | **ممتازة نسبيًا** (عبر لقطات الخادم/Hypervisor في المعمل) |
| **التكلفة والموارد الإضافية** | يستهلك `RAM/CPU/SSD` من المضيف المشترك + يحتاج ترخيص ضيف ووسائط تثبيت | لا يستهلك عتاد VM إضافي، لكنه أضعف أمنيًا وتشغيليًا | يعتمد على توفر موارد وتراخيص لدى إدارة النظم بالجامعة (`UNKNOWN`) |

> **الخلاصة المقارنة:** يُوصى **بالخيار (1: Standalone VM)** لأنه يوفر عزلًا منطقيًا ونظاميًا قويًا على الجهاز المحلي يفصل نظام التشغيل والشبكة والشهادات عن المثيل المشترك `MSSQLSERVER` ويتفادى عدم دعم `Windows 11` — مع الإقرار الصريح بأن العزل **ليس مطلقًا** (لاشتراكه في موارد المضيف والـ`Hypervisor` واحتمال المخاطر المتبقية عند سوء تهيئة الشبكة أو المشاركة)، وبقاء كافة قيود حماية `MSSQLSERVER` الحالي سارية دون تخفيف. ويُحتفظ **بالخيار (3)** بديلًا احتياطيًا إذا لم تسمح موارد جهاز المالك أو التراخيص بإنشاء VM محلية.

## 6. خطة الشبكة وحماية الأصل والأمان (`TLS 1.2` والشهادات والمصادقة)

### أ) عزل الشبكة وحدود `Host-Only` وصلاحيات الوصول
1. **شبكة معزولة وحدود `Host-Only / Internal Switch`:** تهيئة محوّل شبكة افتراضي خاص بين المضيف والضيف فقط دون `Bridged Adapter` أو `NAT` غير مصرح به ودون ربط بشبكة الجامعة أو تعريض منفذ `1433` للخارج؛ مع **تعطيل مشاركة المجلدات (`Shared Folders`) وإعادة توجيه الأقراص (`Drive Redirection`) والحافظة المشتركة غير الضرورية** لتقليص المخاطر المتبقية، مع الوعي بأن عزل `Host-Only` منطقي ويعتمد على سلامة نظام المضيف وإعدادات الـHypervisor.
2. **جدار الحماية (`VM Guest Firewall`) وموارد المضيف:** السماح بالوصول إلى منفذ محرك SQL في الضيف فقط من عنوان IP الخاص بالشبكة الداخلية للمضيف المعزول؛ وتقييد ذاكرة الضيف (`Max Server Memory`) لمنع استنزاف موارد المضيف المشترك مع `MSSQLSERVER`، وإيقاف `SQL Server Browser` إن لم يكن ضروريًا واستخدام منفذ ثابت صريح.
3. **فصل التسمية والإعدادات:** تسمية الـVM بوضوح (`PayrollReview-SQL2014-Lab`)، وعدم حفظ أي أسرار أو `Connection Strings` في Git؛ استخدام `dotnet user-secrets` أو متغيرات بيئة محلية مؤقتة للـPoC مع حجب الأسماء/العناوين في التقارير.
4. **أقل صلاحيات (`Least Privilege`):**
   - فصل حساب إعداد القاعدة الاختبارية (`P3`) عن حساب تشغيل اختبارات `PoC` (`P4`) — يُنشأ مستخدم معملي محدود الصلاحيات على `PayrollReview_CompatLab_Synthetic` فقط (`db_datareader`, `db_datawriter`، وصلاحية تنفيذ/DDL مقصورة على القاعدة الاصطناعية إذا تطلبتها الاختبارات)، وتجنب استخدام `sa` في اختبارات التطبيق.
5. **منع الاتصال التلقائي الخاطئ:** عدم وضع `localhost` أو `.` أو أي اسم يشير للمثيل المشترك أو خوادم الجامعة في إعدادات `PoC`؛ اشتراط التحقق من اسم السيرفر المعزول داخل الـPoC قبل فتح أي معاملة.

### ب) متطلبات `TLS 1.2` والمصادقة (`KB3135244`)
- لماذا **`SQL Server 2014 SP3`** إلزامي هنا؟
  1. لضمان التوافق الرسمي مع `Windows Server 2019` أو `Windows 10` (`Yes (SP3)` في `KB2681562`).
  2. لتحقيق دعم `TLS 1.2` الأصلي على محرك `SQL Server 2014` وفق `KB3135244` (وتجاوز قصور `12.0.2269.0 RTM GDR`).
- **إعداد شهادة الاختبار وسلسلة الثقة (`Trust Chain`):**
  - إنشاء شهادة خادم للـLab صادر عن `Internal Lab CA` مؤقتة (مُضمَّن فيها الاسم المرجعي/SAN الصحيح للـLab)، مع استيراد جذر `Lab CA` إلى مخزن الثقة في المضيف للمعمل **فقط** (أو التحقق الصريح عبر `ServerCertificate` في `Microsoft.Data.SqlClient`).
  - اختبار الاتصال في PoC بالوضع الآمن **`Encrypt=Mandatory`** (`true`) **دون** وضع `TrustServerCertificate=True` و**دون** `Encrypt=False` كحل التفافي.
  - **إثبات إصدار البروتوكول مستقبلًا (`TLS 1.2` Proof):** ظهور `encrypt_option = TRUE` في `sys.dm_exec_connections` يثبت وجود تشفير للاتصال فقط، لكنه **لا يثبت وحده** أن الإصدار المتفاوض عليه هو `TLS 1.2`. عند تنفيذ `P2` أو `TC01` مستقبلًا بعد تفويض مستقل، يجب تقديم دليل مستقل لإصدار البروتوكول المتفاوض عليه (مثل سجل `Schannel` موثوق على الضيف/المضيف، أو `trace` تشخيصي لطبقة TLS، أو التقاط حزم شبكة المعمل المعزولة مع طمس البيانات الحساسة).
  - إذا تعذر إثبات إصدار `TLS 1.2` بدليل مستقل فلا يُحتسب الاختبار `PASS` بل تُسجل الحالة **`BLOCKED_TLS_VERIFICATION`**؛ وإذا تعذر تحقق `SP3` أو ثقة الشهادة تُسجل الحالة **`BLOCKED_TLS`** ولا يُخفض مستوى التشفير مطلقًا.

## 7. خطة تنفيذ اختبارات `Phase B` في المعمل المعزول (`TC01..TC11: NOT_RUN`)

تبقى جميع الاختبارات في هذه الخطة بحالة **`NOT_RUN`** إلى حين اجتياز البوابات `P0..P3`. يُنفَّذ الـPoC لاحقًا باستخدام `.NET 10` في مشروع تجريبي منفصل خارج `src/**` و`client/**` (مع الحفاظ على فصل `Core/Application/Infrastructure` داخل الـPoC نفسه وتجريب `Microsoft.Data.SqlClient 6.1.8` و`Dapper 2.1.89` الاختياري — تبقى صفة حزمة `SqlClient` أنها `SUPPORTED` على `.NET 10` و`OUTSIDE_CURRENT_SUPPORT_MATRIX / UNVERIFIED` على `SQL 2014` حتى نجاح كل الاختبارات):

| المعرّف | الشرط المسبق (`Precondition`) | إجراء الاختبار المخطط (`TC` Verification) | معيار القبول (`PASS Criteria`) | نوع الدليل المحجوب البيانات | الحالة الآن |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`TC01`** | اجتياز `P2` + إذن `P3` | فتح اتصال آمن (`Encrypt=Mandatory` وشهادة Lab CA موثوقة) وتنفيذ استعلام هوية الخادم: `SELECT 1 AS Ok, @@VERSION AS VersionText, SERVERPROPERTY('ProductVersion') AS ProductVersion, SERVERPROPERTY('ProductLevel') AS ProductLevel;` ثم استعلام مستقل لمستوى توافق القاعدة الاصطناعية من `sys.databases`: `SELECT name, compatibility_level FROM sys.databases WHERE name = N'PayrollReview_CompatLab_Synthetic';`، مع جمع دليل مستقل لإصدار TLS المتفاوض عليه (`Schannel` أو `trace` تشخيصي أو التقاط شبكة المعمل المعزولة مع طمس البيانات) | نجاح الاتصال بـ `TLS 1.2` مثبتًا بدليل بروتوكول مستقل (لا يكفي `encrypt_option = TRUE` وحده؛ وعند عدم إثبات الإصدار تُسجل **`BLOCKED_TLS_VERIFICATION`** لا `PASS`)، وقراءة `ProductVersion` (`12.0.6xxx`) و`ProductLevel = N'SP3'` عبر `SERVERPROPERTY`، وقراءة `compatibility_level = 120` للقاعدة الاصطناعية من `sys.databases` دون `TrustServerCertificate=True` | سجل ناتج `ProductVersion` و`ProductLevel` و`compatibility_level` و`encrypt_option = TRUE` + الدليل المستقل لإصدار `TLS 1.2` مع حجب اسم الجهاز والـIP وأي بيانات حساسة | **`NOT_RUN`** |

## 8. خارطة البوابات والموافقات المستقلة المستقبلية (`P0` إلى `P5`)

لا يُسمح بأي قفزة إلى الأمام أو دمج خطوتين دون تفويض صريح لكل بوابة:

```text
[P0: جمع مواصفات الجهاز/التراخيص Read-Only بعد إذن المالك]
   └──> موافقة المالك المستقلة 1
         [P1: إنشاء VM معزولة + Windows متوافق + SQL 2014 SP3 + Lab CA + Snapshot]
            └──> فحص إثبات العزل والتشفير
                  [P2: تحقق Read-Only (0 قواعد مستخدمين + الشبكة المعزولة + TLS 1.2)]
                     └──> موافقة المالك المستقلة 2
                           [P3: إنشاء قاعدة PayrollReview_CompatLab_Synthetic فقط]
                              └──> تنفيذ المعمل غير المدمج
                                    [P4: تشغيل PoC وجمع أدلة TC01..TC11 محجوبة البيانات]
                                       └──> مراجعة ChatGPT + قرار المالك
                                             [P5: رفع تقرير نتائج Phase B ثم ADR مستقل لاختيار المزود]
```

| البوابة | المالك للقرار / المنفذ | المسموح بالضبط | الشرط المانع للانتقال (`Stop Gate`) |
| :--- | :--- | :--- | :--- |
| **`P0`** | إذن المالك -> فحص من Gemini | فحص قراءة فقط لإمكانيات جهاز المالك وتوافر التراخيص ووسائط ISO | تعارض موارد المضيف أو انعدام تراخيص صالحة لـ `Guest OS` / `SQL 2014` |
| **`P1`** | موافقة المالك المستقلة -> تجهيز الـVM | إنشاء `VM` معزولة، شبكة `Host-Only`، تثبيت `Guest OS` + `SQL 2014 SP3` + `Lab CA`، وأخذ **`Snapshot 0`** نظيف | أي استخدام أو مساس بـ`MSSQLSERVER` الحالي أو كسر عزل الشبكة |
| **`P2`** | Gemini -> مراجعة ChatGPT | التحقق بقراءة فقط من `0` قواعد مستخدمين، رقم البناء `SP3`، وتفاوض `TLS 1.2` عبر TCP بدليل بروتوكول مستقل (`Schannel` أو `trace` تشخيصي أو التقاط شبكة معملية مع طمس البيانات) | فشل التشفير الآمن -> **`BLOCKED_TLS`**؛ عدم ثبوت إصدار `TLS 1.2` بدليل مستقل -> **`BLOCKED_TLS_VERIFICATION`** (لا `PASS`)؛ أي تسرب شبكي -> **`BLOCKED_ISOLATION`** |
| **`P3`** | موافقة المالك المستقلة -> إنشاء قاعدة الاختبار | إنشاء قاعدة واحدة فقط: `PayrollReview_CompatLab_Synthetic` ببيانات اصطناعية وحساب معمل مقيد | غياب الموافقة الصريحة على الكتابة (`BLOCKED_OWNER_PERMISSION`) |
| **`P4`** | Gemini | تشغيل `PoC` خارج `src/**` لـ`TC01..TC11` وتوثيق الأدلة المحجوبة البيانات | استخدام أي بيانات حقيقية أو خفض إعدادات التشفير |
| **`P5`** | مراجعة ChatGPT -> قرار المالك | رفع Draft PR توثيقي بنتائج `Phase B` الفعلية، ثم فتح `ADR` مستقل لاختيار المزود | **لا دمج لكود أو إضافة NuGet إنتاجية أو إنشاء Schema قبل اعتماد ADR مستقل وبوابات التصميم** |

## 9. خطة الرجوع والتوقف الطارئ وتنظيف المعمل (`Rollback & Stop Criteria`)

1. **نقاط الاستعادة (`VM Snapshots`):** أخذ لقطة نظيفة للـVM (`Snapshot-Clean-SP3-PreLabDB`) بعد `P2` وقبل `P3`، بحيث يمكن إعادة المعمل إلى حالة الصفر النظيفة فورًا بعد `P4` أو عند أي خلل.
2. **محفزات التوقف الفوري (`Mandatory STOP`):**
   - الاشتباه في اتصال أو توجيه شبكي يصل لقاعدة بيانات الجامعة أو `MSSQLSERVER` ذي الـ13 قاعدة.
   - عدم إمكانية تحقيق `TLS 1.2` + ثقة الشهادة عبر `SP3` (`BLOCKED_TLS`) أو تعذر إثبات إصدار `TLS 1.2` بدليل بروتوكول مستقل (`BLOCKED_TLS_VERIFICATION`).
   - محاولة استخدام بيانات حقيقية أو كلمات سر في أي ملف متتبع بـ Git.
   - غياب إذن المالك المستقل عند أي انتقال بين `P0..P5`.
3. **ضوابط حماية الأسرار وطمس الأدلة:**
   - حذف أية ملفات/سكربتات أو قواعد مؤقتة (`DROP DATABASE PayrollReview_CompatLab_Synthetic` فقط على الـVM المعزولة، أو الرجوع للقطة `Snapshot`) بعد انتهاء `P4`.
   - حجب أسماء الأجهزة، عناوين IP، حسابات التشغيل، وسلاسل الاتصال بالكامل قبل نشر أي تقرير على GitHub.
