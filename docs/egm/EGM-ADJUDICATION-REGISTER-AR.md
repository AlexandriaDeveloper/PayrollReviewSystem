## 1. ملخص تنفيذي وحدود الصلاحية

1. **التمييز بين أربعة أمور منفصلة:**
   - **وجود التقارير (`REPORTS_PRESENT`):** توجد ستة تقارير في [docs/egm/reports/](reports/) إضافةً إلى التقرير الموحّد في جذر المستودع (`../../consolidated_review_report.md`) ونسخته المكررة في (`consolidated_review_report.md`).
   - **استقلال التشغيل (`INDEPENDENCE_UNVERIFIED`):** احتواء التقارير على خانة ذاتية (`FreshContextVerified: YES`) لا يثبت استقلال التشغيل بمفرده؛ إذ سجلت [Issue #27](https://github.com/AlexandriaDeveloper/PayrollReviewSystem/issues/27) نتيجة الفحص المباشر المؤرخة 8 نوفمبر 2026 بعدم وجود استدعاءات `manage_subagents` أو Artifacts وقت الفحص، كما بقيت [Issue #30](https://github.com/AlexandriaDeveloper/PayrollReviewSystem/issues/30) بحالة `NOT_RUN`. وعليه فالحالة الدقيقة للتقارير الستة هي **`REPORTS_PRESENT_INDEPENDENCE_UNVERIFIED`**.
   - **صحة الملاحظة مقابل اعتماد العلاج (`Critique Validity != Proposed Fix Approval`):** قد تكون الملاحظة صحيحة في رصد ثغرة أو غموض توثيقي (`ACCEPT_FINDING`)، بينما يكون العلاج الذي اقترحه تقرير Goldfish مرفوضًا لتعارضه مع ثوابت المشروع أو مواصفاته (`REJECT_WITH_EVIDENCE`).
   - **ترشيح Gemini مقابل الاعتماد:** التصنيفات الواردة هنا ترشيح تحكيمي أولي للمراجعة مع ChatGPT وقرار المالك؛ لا يملك Gemini اعتماد قواعد قانونية أو هجرات SQL أو تنفيذ `Core/Application` من تلقاء نفسه.

2. **الهدف العملي (`Core-First`):** إزالة الموانع التوثيقية والخلط المفاهيمي على طريق مواصفة دورة الملاحظة والرد والحسم ومتابعة الفروق (`D-029` / `P-017`) وحدود `Core/Application`، مع وسم كافة الملاحظات غير الأولوية صراحةً بحالة **`NOT_ADJUDICATED_YET`**.

## 3. فواصل العمل الإلزامية قبل التحكيم (تطبيق D-028 / D-029 / P-017)

تلتزم مصفوفة التحكيم بالفصل الحتمي بين المفاهيم الآتية دون أي دمج أو افتراض آلي:
1. **`Reporting of Deduction` مقابل `Verified Settlement`:** ظهور استقطاع أو فرق مبلغ في كشف Oracle أو إدخال المصدر (`ReportedDisbursementAmount` / `SourceAmount`) **لا يثبت** سداده أو توريده أو خصمه الفعلي المحقق (`VerifiedPaidAmount` / `Verified Settlement`) إلا بسند تسوية مستقل معتمد.
2. **`Finding Resolved` مقابل `Financial Follow-up Closed`:** حسم صحة الملاحظة المالية أو سحبها بعد تقديم الرد والمستند (`Finding Resolved` / `Withdrawn`) لا يغلق مسار متابعة تنفيذ الفرق المالي أو استرداده/تصحيحه رسميًا (`Financial Follow-up Closed`) إلا بعد إثبات التسوية أو القرار المالي المخول.
3. **حفظ القيم السبع مستقلةً (`AUDIT-FINDINGS-AND-DECISIONS.md`):** `SourceAmount`، `ExpectedAmount`، `ReviewedAmount`، `OfficialCorrectionAmount`، `ReportedDisbursementAmount`، `VerifiedPaidAmount`، و`OutstandingAmount`.

## 4. مصفوفة تحكيم أولويات `Core-First` و`D-029 / P-017`

> **دليل حالات التصنيف المرشح:**  
> - `ACCEPT_FINDING`: الملاحظة دقيقة في رصد ثغرة أو غموض توثيقي فعلي (دون لزوم قبول علاج التقرير).  
> - `REJECT_WITH_EVIDENCE`: الادعاء أو العلاج المقترح يتعارض مع نص مواصفة قائمة أو حقيقة برمجية/مؤسسية موثقة.  
> - `NEEDS_SPECIFICATION`: الملاحظة تكشف تفصيلًا برمجيًا/تعاقديًا يحتاج حسمًا في مرحلة المواصفة (`D-029/P-017` أو شريحة `Core/Application`) قبل أي كود أو SQL.  
> - `REQUIRES_OWNER_DECISION`: المسألة تتطلب قرار عمل/صلاحيات/قانونًا صريحًا من المالك (يُحال لما يناسبه في [Issue #39](https://github.com/AlexandriaDeveloper/PayrollReviewSystem/issues/39)).  
> - `UNVERIFIED`: ادعاء غير مدعوم بدليل مستقل قابل للتحقق حاليًا (مثل استقلال عزل السياق).

## 6. أسئلة المالك الحاسمة لدورة `D-029 / P-017` والحدود (مرتبطة بـ [Issue #39](https://github.com/AlexandriaDeveloper/PayrollReviewSystem/issues/39))

الأسئلة الآتية مُصاغة لكي يجيب عنها المالك ضمن مسار [Issue #39](https://github.com/AlexandriaDeveloper/PayrollReviewSystem/issues/39) دون المساس بحالتها أو اختراع أي قواعد قانونية أو جداول SQL:

1. **صلاحيات الحسم وسحب الملاحظة وإغلاق المتابعة المالية (`BLK-05` / `D-029` / `P-017`):**  
   ما الصلاحيات الدقيقة لكل من: (أ) تسجيل الرد الداخلي من المركزية أو الخارجي عبر موظف الوحدة؛ (ب) اعتماد **سحب ملاحظة** (`Withdrawn`) إذا ثبتت سلامة المصدر؛ (ج) اعتماد ترحيل فرق استقطاع أو ربطه ببند آخر؛ (د) إغلاق **المتابعة المالية** (`Financial Follow-up Closed`) بعد حسم الملاحظة؟
2. **حسم اعتماد الشهر مع بقاء فرق متابعة أو بند ثانوي بحالة `UNKNOWN` (`MAJ-02` / `DES-01-011`):**  
   هل يُسمح للمراجع بإغلاق فحص البنود المكتملة الدليل للموظف في الشهر بينما يبقى استقطاع ثانوي أو متابعة فرق مالي مفتوحةً (`FollowUpPending` / `UNKNOWN`)، أم يمنع ذلك اعتماد صرفية الشهر للموظف حتى التحقق؟
3. **نطاق فرادة المرتب الرئيسي عبر الوحدات وأثر صرفية منفصلة ورعاية الطفل (`BLK-02` / `BLK-12` / `MAJ-21`):**  
   - هل يمكن لشخص امتلاك علاقتي تعيين نشطتين معًا أم تقع الفرادة على `EmploymentRelationshipId` (وما الحل عند انتقال الموظف بين وحدتين حسابيتين مختلفتين داخل الشهر)؟  
   - هل تُربط تسوية رعاية الطفل مع استمارة 132 ع.ح داخل نفس الشهر على أنهما جزءان لمراجعة `MonthlyMainSalarySlot` واحدة؟  
   - هل اعتماد/رفض صرفية `SEPARATE` مستقل تمامًا عن حالة اعتماد `AuditCase` للمرتب الرئيسي أم قد يوقفه؟
4. **حدود الإدخال المباشر ومستند إثبات التسوية الفعلية (`MAJ-03` / `Q-04`):**  
   - هل يكفي في الإدخال المباشر للموظف (دون ملف) حفظ المراجع بصفته ومسؤوليته للمقارنة الأولية (`Draft` -> `Submitted`) أم يُشترط مراجع ثانٍ قبل أي اعتماد؟  
   - ما هي المستندات المعتمدة داخل الوحدة لإثبات وصول الصرف أو التسوية الفعلية (`VerifiedPaidAmount`) بدل الاكتفاء بظهور المبلغ في كشف الصرف؟
5. **نطاق وتوقيت إعادة تشغيل Goldfish المستقلة لاحقًا ([Issue #27](https://github.com/AlexandriaDeveloper/PayrollReviewSystem/issues/27) و[Issue #30](https://github.com/AlexandriaDeveloper/PayrollReviewSystem/issues/30)):**  
   متى يقرّر المالك تشغيل جولة Goldfish مستقلة موثقة بـArtifact وسجل استدعاء Subagent فعلي لمواصفة `D-029/P-017` وخريطة `DDD/SOLID` (`Issue #30`) تمهيدًا لأول شريحة `Core/Application` وفق ترتيب [Issue #56](https://github.com/AlexandriaDeveloper/PayrollReviewSystem/issues/56)؟
